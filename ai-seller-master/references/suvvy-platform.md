# Suvvy.ai — универсальная платформенная инструкция

Источник: документация Suvvy ([llms.txt](https://docs.suvvy.ai/ru/llms.txt)) + рабочие боты Avito (Instructions, Direct Questions, таблицы, Bitrix).

Как писать текст Instructions: [suvvy-prompt-rules.md](suvvy-prompt-rules.md).  
Таблицы: [table-setup.md](table-setup.md).  
Скелет промпта: [instructions-template.md](instructions-template.md).

## Слои знаний (порядок)

1. **Instructions** — оркестрация, тон, запреты, когда вызывать функции.
2. **Вопрос — ответ (Direct Questions)** — факты; вызов `get_file_text("Exact Title")`.
3. **Таблицы (CSV/XLS/Google)** — остатки, прайс-строки; функции поиска.
4. **Действия** — LLM-вызов или триггер (webhook, Bitrix native, сообщение).
5. **Интеграции на файле DQ** — смена статуса CRM / оператора при `get_file_text`.

Не класть все прайсы в Instructions. Не дублировать противоречащие правила в трёх местах: **промпт побеждает**, DQ дополняет факты.

## Instructions — рекомендуемые секции

Suvvy UI часто ждёт ROLE/GOALS. Сохранять смысл:

| Секция | Содержание |
|--------|------------|
| `#ROLE` | Роль, канал, сайт, out of scope. Не выходить из роли. |
| `#GOALS` | Ценность в чате → квалификация → CRM при правилах → soft call / chat-only. Дожимы не задача бота. |
| `#GREETING` | Привет **один раз**; не повторять, если канал уже поприветствовал. Не «Чем могу помочь?» если запрос уже есть. |
| `#RESPONSE LANGUAGE` | Язык **последнего** сообщения клиента. |
| `#RESPONSE STYLE` | Человек в чате, 1–3 предложения, без корпоратива. Мало «отлично/спасибо». |
| `#LOGIC` | Шаги диалога + ветки (продукт, наличие, визит, large/medium/small). |
| `#WORKING WITH FUNCTIONS` | Когда какой `get_file_text` и таблица. |
| `#RESTRICTIONS` | Запреты, совпадающие с `hard-bans.md`. |
| `#IMPORTANT` | CRM ≠ конец диалога; менеджер может войти в любой момент. |

Temperature: **0–0.3**.

## Direct Questions

- Заголовок в UI = строка в промпте **точно** (регистр, пробелы).
- Включить тумблер.
- Предпочтительно **< ~50** записей.
- Правка: `sources/foo.md` → `suvvy-qa/NN-foo.md` → вставить в Suvvy.
- Формат paste-файла:

```markdown
# Suvvy Direct Question — paste into «Вопрос — ответ»

**Title (exact):** `Human Readable Title`

**Answer / body:**
...
```

Импорт Excel: скрипт `build_xlsx.py` из тел DQ.

**Не грузить в бота:** follow-ups / дожимы (отдельное приложение).

## Таблицы

Проблема «бот не находит название»:

- Ищет целое предложение вместо **токена** из всего чата.
- Ищет одну колонку, а имя в RU/EN/типе/описании.
- BOM в CSV ломает имя первой колонки → UTF-8 **без BOM**.
- Одна функция в UI, в промпте другое имя → **два подключения одного CSV** (primary + fallback).

Универсальный поиск:

1. Токен из **всей** переписки (выбросить «есть ли», «в наличии», тип изделия).
2. Не искать одно общее слово категории без имени (`мрамор`, `бухгалтер` как единственный фильтр).
3. Колонки по очереди: `search_text` → `search_aliases` → имя RU → имя EN.
4. Предпочесть «в наличии» / `in_stock=yes`; если пусто — без фильтра.
5. Max **5** строк, пока клиент не просит полный список.
6. Использовать **всю строку** (размеры, цена, статус, фото-ссылки).
7. Пусто после лестницы ретраев → менеджер, **не** «нет в базе» / «такого нет».

Описание функции таблицы в UI: LIKE, без регистра, «передавай только название, не фразу клиента».

Скрипт сборки CSV: нормализация, алиасы опечаток, `search_text` из нескольких столбцов источника.

## Действия (Actions)

Два режима:

- **Вызов LLM-моделью** — модель сама решает по **описанию функции**. Описание = когда вызывать + что делает + один раз за диалог + клиенту не говорить про CRM.
- **Вызов по триггеру** — слово/файл/функция.

Параметры шага (имя, описание) задаются один раз на действие.

Native Bitrix в Suvvy:

- Тип: Лид или Сделка — как в CRM клиента.
- **ID сущности / контакта** — переменные через **шестерёнку** (текущий лид диалога), не хардкод.
- **Статус** — **куда** переводим (например «В работе»). «Откуда» обычно не выбирается: лид уже в «Неразобранное».
- После успеха можно «прервать шаги».

Предпочтительный паттерн для воронки (меньше рассинхрона имён действий):

**CRM-сдвиг вешать на Direct Question** (`get_file_text("Bitrix Funnel Stage")`) + вкладка Integrations: смена статуса + свободный оператор.

Если отдельное LLM-действие: одно имя на всю систему; в промпте и UI одинаково; не ждать телефон на structurally large.

## Bitrix / Open Lines (универсально)

- Бот отвечает в статусах, выбранных в канале (или во всех, если не задано).
- Смена статуса ≠ сообщение клиенту «я передал в CRM».
- После сдвига: квалификация продолжается, пока оператор не забрал чат (платформа глушит бота).
- Телефон → отдельный DQ уведомления в Telegram, если так заведено.
- Поля карточки: не выбирать десятки полей (токены/цена). Если бот заполняет карточку — явная фраза в Instructions.

## Каналы

Avito: короткий первый ответ, без простыни спеки.  
Не слать полный каталог на «где посмотреть», если живой визит — сначала адрес/выезд (нишевое правило, но паттерн: **не сваливать ссылки**, пока не попросили онлайн).

## Язык и тон (платформа)

Ответ на языке **последнего** сообщения клиента. Короткие реплики. Не превращать чат в анкету.

## Notification (телефон)

Отдельный DQ, типичный title: `Notification in telegram`.  
Триггер: валидный номер в чате. Confirm коротко. Не просить номер снова. Не выдумывать chat_id. После номера не разгонять новую анкету (менеджер уже может звонить). CRM вызвать, если ещё не вызывали (правило D).

## Что не класть в этого бота

- Follow-ups / дожимы (отдельное приложение или настройки фоллоу-апов Suvvy — выбрать одно).
- Голосовой обзвон, рассылки, сторис из чата — другие продукты платформы.
- Хардкод Bitrix ID статусов в текст клиенту (`UC_XBWG2F` и т.п. — только в UI Integrations).

## Эволюция CRM-вызова (не повторять путаницу)

Исторически в одном боте сменялись: webhook `bitrix_move_funnel_stage` → LLM-действие `bitrix24_sync_contacts` → **DQ `Bitrix Funnel Stage` + Integrations**. Для новых ботов сразу паттерн DQ+Integrations, одно имя в промпте.
