# Правила инструкций Suvvy (платформа)

Источник: [Правила написания инструкций](https://docs.suvvy.ai/ru/osnovnye-nastroiki/prompts/prompts/pravila-napisaniya-instrukcii.md), чек-лист формата БЗ, таблицы.

Документация: https://docs.suvvy.ai/ru/llms.txt  
Уточнение страницы: `GET {page}.md?ask=вопрос`

## Три принципа

1. **Лаконичность** — не размазывать квалификацию лишними осями (бренд, «нравится ли»).
2. **Точность** — не «запроси ФИО и телефон», а «шаг за шагом, следующий вопрос только после ответа».
3. **Одна правда** — не дублировать расчёт цены в двух секциях (модель берёт **нижний** кусок и меняет порядок вызовов).

Промпт побеждает при конфликте с DQ. DQ = факты. Не копировать противоречащие правила в три места.

## Утвердительные запреты

Плохо: «Не говори реквизиты».  
Хорошо: «Тебе запрещено предоставлять реквизиты».

В `#RESTRICTIONS` писать `It is forbidden to` / `Тебе запрещено`.

## Полезные формулы Suvvy

- «Шаг за шагом, только после ответа собеседника»
- «…если это ранее ещё не известно из контекста диалога»
- «Всегда» — для критичных вызовов функций
- «Если клиент написал …» — ветка

Буквальность: «Всегда здоровайся» → здоровается **каждый** ответ. Нужно: «при начале диалога» + «не повторять, если канал уже поприветствовал».

## Temperature и объём БЗ

- Temperature агента-продавца: **0–0.3**.
- Direct Questions держать **тонкими**, ориентир **< ~50** записей.
- Большие PDF/регламенты → Документы (вектор), не 200 DQ.
- Точные SKU/цены/остатки → Таблицы + функция, не « intelligently найди в промпте».

## Когда обязательно `get_file_text`

- Заголовок DQ плохо соотносится со смыслом («Bitrix Funnel Stage» ≠ вопрос клиента).
- Смена этапа CRM / побочный эффект Integrations на файле.
- Сценарии, которые модель иначе «угадывает».

В промпте: «если ситуация X → get_file_text("Exact Title")». Заголовок **байт-в-байт**.

Документы: смысловой поиск (`search_in_knowledge_base` и аналоги). Для продавца Avito предпочтительны **явные DQ**, не надежда на вектор прайса.

## Быстрые ответы vs Документы vs Таблицы

| Данные | Куда |
|--------|------|
| Правила диалога, квалификация, адрес, bans | Instructions + DQ |
| FAQ, политики, «как вернуть» | Документы или DQ |
| Прайс, остатки, слоты, филиалы | Таблицы + функция |
| Часто меняется | Таблицы |
| Редко меняется текст | DQ / документы |

Импорт DQ: Excel колонки Title / Search Title / Content / Used. Скрипт `build_xlsx.py`. Follow-ups-файл в SKIP.

## Действия

- Вызов моделью: качество = **описание функции** (когда, один раз, клиенту не говорить).
- Вызов по триггеру: файл / слово / другая функция — стабильнее для CRM.
- Предпочтение воронки: Integrations **на DQ** (`get_file_text("Bitrix Funnel Stage")`) — смена статуса + свободный оператор. Не плодить `bitrix24_sync_contacts` + webhook + DQ сразу.
- Bitrix: тип Лид/Сделка как в CRM; ID через **шестерёнку**; статус = **куда** («В работе»). «Откуда» обычно не выбирается (Avito → «Неразобранное» / `NEW`).
- Старый webhook Bitrix — менее предпочтителен, чем Marketplace / native.

## Фоллоу-апы платформы

В Suvvy есть фоллоу-апы и динамические пинги. Для этого мастера продаж: **не обещать** в чате и **не дублировать** логику дожима в Instructions, если дожимы живут в отдельном приложении. Иначе два пинга.

## Прочее платформенное (знать, не тащить в каждый бот)

- Голосовой агент / исходящие — другой тип промпта (компактнее).
- Мультиагентность, вебхуки, чтение URL, обработка файла клиента, картинки.
- amoCRM / Kommo / RetailCRM — те же принципы CRM: один раз, не рассказывать клиенту, ID из переменных.
- Каналы: Avito, WB, Ozon, TG, виджет — тон и длина первого ответа короче на маркетплейсе.
- Open Lines: бот молчит, когда оператор забрал чат — клиенту это не объяснять.
- Целевые действия / теги аналитики — не путать с CRM-стадией.
- Аудит инструкции в UI Suvvy — прогонять после крупных правок.

## Отладка

Экспорт чата: смотреть, **вызывалась ли** функция, какой аргумент (предложение vs токен), пустая таблица, повтор действия. Типовые ошибки «агент молчит» — в доке «Типовые ошибки»; не лечить удлинением ROLE.
